## Open defects

[ ] Stale output survives the removal of a specification. Deleting a .spectable
    leaves its generated test behind, and the shared files keep its entries:
    SourceScan::dropEntriesForMissingFiles is not applied to Java's
    TableHelper/ProductionHelper, Rust's lib.rs, the TypeScript/JavaScript
    production/index, or a stale dist/. A removed specification should take
    its generated code with it.

[ ] A docstring marker is highlighted for only its first two characters. The
    three quote marks that open or close a docstring get colour on two of
    them. Cosmetic, in the editor's highlighter.

[ ] ExampleTests is stale, and 2026-10-25 established exactly how. A full
    regeneration in all nine languages produces, beyond the specification
    copies:

    - RecordFilterExample in every language loses one example row and gains a
      spelling fix in a Description. The source specification was edited and
      the language folders were never regenerated, so the committed tests
      assert a row the specification no longer has.
    - the six C++ cell wrappers under CPlusPlus/ExampleTests/common/ gain
      their comparison operators and empty(), which is the fix made for the
      external findings report. The other eight languages' shared files are
      current.

    That regeneration was done and then reverted, deliberately: verifying it
    means running nine suites, and the run was stopped part-way when the
    machine ran short of memory. Java was the one language that did run, on
    the regenerated files: 39 tests, 0 failures, and the regenerated
    Record_Filter_Example_Test passed 5/5. AddressCorrection errored twice on
    the network (SSL handshake to the Census geocoder), which is the live
    service and not a defect. So: regenerate all nine and run all nine in one
    deliberate pass, with the network up.

    Two things checked the same day so they are not assumed again: every one
    of the nine languages does have committed AddressCorrection output, and
    Go's production constructor takes lowercase parameters while its fields
    are correctly cased, which is ordinary Go. The AddressCorrection half of
    "bug to fix.txt" is still the open piece of that file.


## Finished since the last survey — recorded here so the list is not re-read

[x] Leading whitespace is ignored. Ken's ruling, 2026-10-25: people may wish
    to indent for their own purposes. The parser used to discard any indented
    line that was not a pipe row -- it served named-comment continuation, and
    served it by dropping the text -- which also swallowed an indented step:
    a scenario with an indented When and Then analyzed clean and generated a
    test holding only the Given. The skip is gone, so every line is read for
    what it says at any column. Four specifications were relying on the
    discard for wrapped prose (Common Types, Types and Formatted Dollar in
    VariousTests, Types in ExampleTests) and now carry the leading backslash
    the syntax document has always asked for, which also means their text
    reaches the comment it was written under for the first time. Documented in
    syntax section 2 and 4.1.1 and in the User Guide; the four corpora are
    back at 67 / 2 / 8 / 0.

[x] The stale Java .spectable copies are deleted. Nineteen of them under
    Java/SpecTableVariousTests/src/test/java/spectable/, every one with an
    authoritative original in TestProject/ and nothing reading them at
    runtime. mvn clean test afterwards: 58 tests, 0 failures.

[x] Rust falls back to a default variant. genRustProductionEnum now derives
    Default with #[default] on the first variant and emits From<&str>,
    From<String> and Display, with the unrecognised value falling back to
    default() because a From cannot fail. Generated, cargo built, and run
    (3/3). Honest footnote: the premise in "More to do.txt" does not hold
    today -- a DataType field crosses into Rust as <Name>Typed text, so no
    generated Rust calls EnumName::from, and the old bare enum compiled fine.
    The fallback is there for production code that does call it, and the
    generated comment points at a fallible parse for the case where the
    unrecognised value matters.

[x] WhenThen is documented. It works just like a When or a Then, and is for
    one table whose columns are part When data and part Then data: the
    scenario has its Given, and the table goes under the WhenThen. In the
    syntax document at 2.7, in the grammar, and at 4.6; in the User Guide
    beside the step keywords. What it generates was read off a run in all
    nine languages -- an ordinary step call handed the whole table, keyword in
    the method name. Two consequences are stated too: an And under a WhenThen
    continues as a WhenThen, and a WhenThen in a Cleanup block is an error.

[x] The external findings report is closed. Every item is fixed, documented,
    or ruled on; the last of them was the most-vexing-parse note, now in the
    User Guide under "Checking that a value is refused".
