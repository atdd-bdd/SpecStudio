### BUG: TableHelper.java is overwritten by each spec, so only the last one's
  grid converters survive. A step whose table is a bare grid typed by a name --
  "Given rolls are : Pins" with a row of values and no header -- generates
  glue that calls TableHelper.toListListPins(values). genTableHelperClass
  (JavaGenerator.cpp:1289) builds the class from collectGlueSigs() for the file
  being generated and writes common/TableHelper.java, replacing whatever was
  there. Every spec in a project shares one output folder, so the last spec
  generated that has any grid table wins and all the earlier ones lose their
  converters.

  Demonstrated: generate bowling.spectable alone and TableHelper has
  toListListPins and toListListBoolean. Generate "Tables and Strings.spectable"
  into the same folder and TableHelper has only toListListString and
  toListListInteger -- the other two are gone, and Bowling_glue no longer
  compiles. This is why the VariousTests Java suite currently fails to build:
  bowling wants toListListPins/toListListBoolean and Formatted Dollar wants
  toListListDollar/toListListFormattedDollar.

  Note toListListBoolean is a BUILT-IN type, so this is not only about
  user-declared DataTypes -- any grid type other than the last spec's is lost.
  Passing every other spec as --context does not help: context blocks are
  skipped when collecting glue signatures.

  Fix: accumulate across the whole generation run rather than per file, the way
  the other common/ classes are written per type. Merging into an existing
  TableHelper would also work but is uglier, since the file would then never
  shrink when a spec stops using a type.

  Java only -- JavaGenerator is the only generator that emits toListList. Check
  whether the other eight have the same hole hidden behind different names, or
  whether they convert grid tables inline. Nothing else exercises a grid table
  of a non-String/Integer type today, so a silent version of this could exist
  anywhere.


### BUG: an unresolvable field type warns but still emits uncompilable code.
  When an Attributes/Entity field names a type the generator cannot convert, the
  converter prints "Unknown type 'X' for field 'y' -- no parse conversion
  available" and then generates the *String -> *Typed class anyway, declaring the
  field as that type and assigning a String to it. The output does not compile,
  so the warning is really an error that lets the build proceed.

  Two ways to reach it, both hit while implementing bowling.spectable:

  1. A DomainTerm used as a field type. checkAttributeFieldTypes in
     SpecTableAnalyzer.cpp explicitly accepts a DomainTerm as a valid field type,
     so Analyze is silent -- but the generator has no conversion for one. The
     spec had "DomainTerm Roll : Pins" and "| Roll1 | Roll | TBR |", which is
     exactly what the analyzer says is legal.
  2. A type that is never declared at all (the same spec's "Score").

  What Java produced for case 1:
      public Roll roll1;                       // no such class anywhere
      this.roll1 = s.roll1;                    // String assigned to Roll
      Json.asString(Json.require(m, "roll1"), "roll1")   // String -> Roll param

  The analyzer and the generator disagree about what a legal field type is, and
  the generator loses. Pick one:
    - resolve a DomainTerm to its underlying DataType when emitting conversions
      ("DomainTerm Roll : Pins" already says Roll is a Pins), and make a
      genuinely unresolvable type an ERROR that stops generation; or
    - make the analyzer reject a DomainTerm as a field type, so the failure is
      reported where the author can act on it.

  The first is better -- it makes the domain vocabulary usable in Attributes
  tables, which is presumably why the analyzer allows it.

  Verified in Java only. The "no parse conversion available" warning comes from
  shared type resolution, so check whether the other eight generators emit the
  same broken shape or merely differ in how they fail.

## Future Enhancements:

### Accept a solution path on the command line. main.cpp ignores argv entirely --
  it builds QApplication, applies the theme, then shows MainWindow with no path
  handling -- so AlignThree.exe always opens empty and the only way into a
  solution is File > Open Solution or the Recent Solutions list.

  Read argv[1], hand it to MainWindow, and let AppController::loadSolution()
  take it from there; ignore a missing or unreadable path and open empty as now
  rather than failing to start. Small change, three payoffs:
    - AlignThree.exe "C:\path\To\X.sspec" works from a shell or a shortcut.
    - Double-clicking a .sspec can open it, once the installer registers the
      file association (scripts/alignthree.iss has no [Registry] section yet,
      so that is a second, separate piece of work).
    - Scripts and agents can launch straight into a solution instead of asking
      someone to click through the GUI.

  Worth deciding at the same time whether a second argument, or a --file switch,
  should also open a named .spectable within that solution.

### Cleanup -  

  #### Analyze-implementation command: flag glue-code methods that are never
  referenced by any step. Not implemented.

  #### When a step name changes, rename/update the corresponding glue method name
  on the next build/analyze instead of leaving an orphaned method. Not
  implemented — AppController::onRenameStep (AppController.cpp:1386) exists
  but only does a find/replace across the .spectable source; it never
  touches already-generated glue method names.

  #### Remove common/ files that are no longer referenced -- DONE.
  Build > Project and Build > Solution now delete every generated
  *String/*Typed file from each output common/ folder before converting
  anything (AppController::clearGeneratedCommonClasses). A whole-project build
  converts every .spectable it owns, so all live classes are written again;
  whatever does not come back belonged to a renamed or deleted AttributeSet.
  Build > Current File deliberately does not do this -- one spec cannot tell
  which classes belong to the specs it was not given.

  The delete runs as a separate pass over all targets before the first
  converter starts. BuildController::run returns as soon as the process is
  spawned, so every conversion is in flight at once and deleting from inside
  that loop would throw away files a sibling had already written.

  Only *String/*Typed go. The JSON reader, the index/module file, YesNo,
  TableHelper and ProductionHelper stay -- they are not per-AttributeSet, and
  converting a single file still expects to find them. The merged index prunes
  itself (see SourceScan.h), so index and files stay in step.

  Two consequences worth knowing:
    - It only clears the output folder of the language whose .specconfig is
      active, so clearing a project takes one build per configuration. Both
      downstream trees have now had all nine run: SpecStudioExampleTests lost
      Pricing, Discounting and Shipping in every language (plus SomeTypes,
      LabelValue and EnumerationValues in Java, which was further out of date),
      and SpecStudioVariousTests turned out to have orphans only in Java.
    - A dead glue method becomes a compile error instead of staying invisible.
      First run deleted PricingString/PricingTyped -- Pricing is in no spec any
      more -- and Shopping_Cart_glue.java still had Then_result_is taking a
      List<PricingString>. That is the intended signal (it is the same dead
      glue the analyze-implementation item above is meant to flag), but it does
      mean the first build after this change can fail to compile until the
      matching glue method is removed.

  #### Production classes are never overwritten -- verified in all nine
  languages: hand-edit a production file, regenerate, the edit survives; and
  with the "create production classes" checkbox off, zero production files are
  written. Working as intended.

  The skip-if-present test no longer keys on the filename. It now looks for a
  *declaration of the type* anywhere under the production folder
  (sourcescan::ProductionScan), so grouping several classes into one file --
  idiomatic Go, normal Rust, mainstream Python -- no longer gets a duplicate
  template written beside the real implementation. When the type is found in a
  differently-named file the run says so:
    INFO:0:Production type 'ShoppingCart' is already implemented in <path>
        - no template written
  Verified per language by concatenating every generated production file into
  one Domain.<ext>, deleting the per-type files, and regenerating: nothing is
  recreated and one INFO line appears per type.

  Still open: renaming an Entity in the spec orphans the implementation.
  ShoppingCart -> Cart leaves the developer's ShoppingCart.cs on disk and writes
  a fresh Cart.cs template; the real implementation is now in the file the tests
  no longer reference, with no warning. Detecting that needs a record of what was
  emitted under which name, so it belongs with the rename-aware cleanup above.

  Also cosmetic: the Python generator writes production/Address.py, where PEP 8
  wants a lowercase module name (address.py). Renaming it would break every
  existing import in both downstream repos, so it needs doing as its own change.

## Bigger Language Feature Ideas (not scoped/designed yet) ---

### Sequence keyword: shows a sequence of operations where each step's Given is
  the previous step's output.

### State table: State/Event grid (states down the side, events across the
  top) filled in with transitions; generates glue code for every
  transition. Shorthand: "Given this state / When this event / Then this
  state." A state's target could reference a Define containing an if-clause
  for more complex transition logic.

### Karnaugh map style DataType/table with don't-cares ("DNC"), checked for
  completeness.

  >10 & <12, =10 | =12" — and/or/not plus comparison operators) instead of
  plain examples; if the rule fields are typed, auto-generate the Examples
  rows from the condition table.

[x] Select a whole block with the mouse, ready for cut/copy: double-click the
    block's KEYWORD, or triple-click any line inside a block. Bound to the
    keyword rather than the whole header line so that double-clicking the
    block's name still selects a word, as it does everywhere else. The selection
    runs from the header through the last non-blank line and takes the line
    break, so Ctrl+X lifts whole lines out and Ctrl+V puts them back as whole
    lines; blank lines between blocks stay put as separators. Two things had to
    be right. Blocks end at the next block keyword, NOT by indentation —
    LineNumberEdit::foldEnd uses indentation, which finds every block empty in
    real specs because they are written flush left (a Scenario and its steps
    share column 0). And a """ docstring can hold anything, including text with
    a leading keyword: include.spectable has Insert "string.txt" inside one, so
    scanning has to step over docstring interiors or that Scenario ends at its
    own docstring. Qt delivers no triple-click event — the third click arrives
    as an ordinary MouseButtonPress — so it is recognised from the time and line
    of the preceding double-click, within QApplication::doubleClickInterval().
    The range rules live in editors/SpecTableBlocks.{h,cpp} as free functions
    over a QStringList precisely so they can be tested without a widget; 17
    assertions pass against the real include.spectable and Calculator.spectable

    block to EOF, unterminated docstring) and the keyword column range, where an
    off-by-one would silently break word selection on the block name. The
    gestures themselves were NOT tested — no GUI automation on this machine.

Share Changes (Commit + Push) / Get Others' Changes (Fetch)

Purpose: help the user review what changed, add a short description, confirm
sharing, and perform Commit + Push in one step — without exposing git jargon
to non-programmers, while still giving programmers what they expect.

Share Changes dialog layout:

1. Summary section (top)
   "You have changes ready to share. Review the updates below, then click
   Share." Shows count of changed items, optional "Last shared on..."
   timestamp, optional "up to date with others' changes" indicator.

2. Change list (center)
   Collapsible list of changed files (e.g. Customer.spec, Order.spec,
   Address.spec). Each expands to a friendly before/after diff view — no
   hunks, no patch syntax. Labels: Added (green), Removed (red), Updated
   (blue). Example:
     Customer.spec
       Name: Ken -> Kenneth
       Age: 42 -> 43

3. Description box (required)
   Label "Describe your changes" / subtitle "This helps others understand
   what you shared." This is the commit message, without calling it that.

4. Advanced options (collapsed, for programmers)
   Show actual git commit message; show commit hash preview; show branch
   name; checkbox "Push immediately after sharing" (checked by default);
   checkbox "Allow empty description".

5. Action buttons
   Primary: "Share Changes". Secondary: "Cancel", "Preview Details"
   (optional). Tooltip: "Saves your changes and makes them available to
   others. (Commit + Push)".

Behavior on Share Changes:
   Validate description -> Commit -> Push -> success toast "Your changes
   have been shared." If push fails: "Your changes were saved, but could
   not be shared. Try 'Get Others' Changes' first, then share again."
   (Programmers will recognize this as commit-succeeded/push-failed.)

Error Recovery dialog ("There Was a Problem Sharing Changes" / "...Getting
Others' Changes"):

1. Friendly summary: "Something went wrong while updating your project. You
   can try again, or ask a developer for help."

2. Simple explanation, one of:
   - Commit failed: "Your changes could not be saved safely."
   - Push failed: "Your changes were saved, but could not be shared with
     others."
   - Fetch failed: "The latest updates could not be downloaded."
   - Merge conflict: "Your changes conflict with updates from others."

3. "Details for Developers" (collapsed by default): real git error text
   (e.g. "Error: non-fast-forward update"), plain-language explanation,
   suggested fix (e.g. "Run: git fetch, then merge or rebase"), buttons
   View Diff / Open Merge Tool / Retry Push / Retry Fetch / Open Terminal,
   and metadata: current branch, remote branch, commit hash, upstream
   status, staged/unstaged changes, conflicting file list.

4. Conflict resolution section (if applicable): friendly message "Some of
   your changes conflict with updates from others. A developer can help
   resolve this." plus developer tools: Open Merge Tool, Show Conflicting
   Files, View Side-by-Side Diff, Abort Merge / Reset (developer only).

5. Action buttons: primary "Try Again", secondary "Cancel"; developer-only
   buttons Retry Commit / Retry Push / Retry Fetch / Open Merge Tool /
   Open Terminal / View Diff.

Related, not yet designed: Conflict resolution dialog, History/timeline
viewer, Branch creation dialog, Status panel, Git onboarding flow for
non-programmers.
