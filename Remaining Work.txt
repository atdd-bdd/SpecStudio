### Replace SpecTableIndex's own reading of the syntax with the parser. The

  behind the generators once and made Analyze report an undeclared type for a
  specification that built. The index already parses every file with

  those parse trees instead, and parseFile, attributeRows, defineInfo and
  collectionElementType deleted. Every remaining regular expression in
  src/analyzer would go with them. About a day, proved the same way: capture

  that moves.

  Small overlap to settle at the same time: checkDomainTermVsDataTypeNames

### A table after a Detail statement. Detail is a named comment today -- a line
  of prose attached to the block above it, carried no further. A BusinessRule is
  often easier to explain in a small table than in a sentence: the conditions
  down one side, what each produces down the other, or a few worked cases that
  are illustration rather than assertion.

  So: allow a pipe table to follow a Detail line, and treat it as part of that
  comment. Documentation, not behaviour -- nothing generated, nothing asserted.
  It differs from an Examples: table precisely in that nothing checks it.

  Worth settling first:
    - Is it only Detail, or every named comment? Description and Notes would
      want the same thing for the same reason.
    - Does it reach the generated code? The "copy named comments into generated
      comments" item below would then have a table to render, which in Java is
      a block comment and in Python a docstring.
    - How does it end -- the first blank line, or the first non-pipe line? A
      Define table ends at the first line that is not a pipe row, and following
      that would be the least surprising.
    - Analyze should say something if such a table looks like an Examples table
      that was meant to be checked: an author who writes conditions and expected
      results under Detail may think they are being tested.

  The parser change is small: Detail is already recognised and skipped, and a
  table after it currently falls to the "no active block" branch. Recording it
  needs a field on the block and a state, like the docstring handling.

### Spell-check the prose in a specification. A specification is mostly words --
  step text, Scenario names, Description and Notes columns, docstrings -- and
  nothing checks any of it today.

  What it needs:
    - camelCase and PascalCase split into their words before lookup, so
      shippingAddress checks as "shipping" and "address" rather than failing as
      one unknown word. snake_case and kebab-case likewise. This is what makes
      it usable at all on a file full of identifiers.
    - a misspelling underlined in the editor, the way a diagnostic is.
    - a context menu on the underlined word offering the suggestions, with
      "Add to Dictionary" among them.
    - "Remove from Dictionary", so a word added by mistake can be taken back.
      Wanted, though less urgent than adding.

  Open questions worth settling before starting:
    - Which dictionary, and where does the user's own live? A project dictionary
      committed with the specifications would let a team share its vocabulary --
      every domain term, every product name -- while a personal one would not.
      Probably both, with the project one in the solution folder.
    - Should a declared name (Entity, Attributes, DataType, DomainTerm, Define,
      every attribute name) be treated as spelled correctly by definition? The
      parse tree already knows all of them, so this is cheap and would remove
      most of the noise before a dictionary is consulted at all.
    - Which regions of the file to check. Checking a table cell holding a value
      would be wrong; checking a Notes column would be right. The parser can
      tell them apart, which is another reason to do this against the model
      rather than the raw text.

  No dependency has been chosen. Qt has no spell checker; Hunspell is the usual
  answer and would be the first third-party library in the IDE, so it needs the
  same look the JSON and HTTP decisions got -- see the note above about curl and
  child processes in the test trees.

### A table of one-line Defines. Today each constant is its own line:

    Define TBR = -1  # Roll has not occurred
    Define TBS = -1  # Score not yet computable

  A specification with a dozen constants would rather say them once, as a table:

    Define
    | Name  | Value  | Notes                     |
    | TBR   | -1     | Roll has not occurred     |
    | TBS   | -1     | Score not yet computable  |

  Each row is exactly a one-line Define -- same scalarValue, same =Name use --
  so the parser is the only thing that changes: a bare "Define" with no name,
  followed by a table whose header has Name and Value, becomes one Define per
  row, at that row's line. Nothing downstream moves; =TBR already resolves in
  step tables, Examples tables and Default columns. Half a day. The one
  decision is what a table-form Define with a *name* means when its header is
  Name | Value -- today that is a vertical key/value Define standing in for a
  step table, and it must keep meaning that.

## Bigger Language Feature Ideas (not scoped/designed yet) ---

### Infer a table's orientation instead of being told it. A step already names
  the attribute set its table belongs to, so the parser knows the attribute
  names before it reads the table. That is enough to tell which way the table
  runs: look for where the *second* attribute's name appears. Across the first
  row means horizontal; down the first column means vertical. One attribute
  alone is ambiguous and either reading gives the same answer.

  Keep the Vertical keyword for now — this would make it optional rather than
  remove it, and an explicit keyword is still worth having where a reader wants
  the orientation stated.

  Groundwork is already done: as of 2026-09-13 a Vertical table is treated as a
  horizontal one transposed everywhere it matters, so missing and unknown
  attributes give the same message either way (converter/SpectableParser.cpp,
  validateStepTables).

### What Karate has that SpecTable does not, from writing API.spectable against a
  live service (SpecStudioVariousTests, 2026-08-13). Karate is an API-testing
  DSL built on Gherkin. The array syntax below was checked against Karate's own
  reference; the single-object example is from knowledge, so confirm that one
  before relying on it.

  The headline difference is that Karate collapses the specification and the glue
  into one file. Everything written for API.spectable -- RestCall, the glue, the
  generated *String/*Typed classes -- is what Karate ships as its DSL, and for
  pure API testing it needs no Java at all:

      Scenario: Retrieve a single post
        Given url 'https://jsonplaceholder.typicode.com'
        And path 'posts', 1
        When method get
        Then status 200
        And match response == { userId: 1, id: 1, title: 'sunt aut...', body: '#string' }

  Two things there were arrived at independently for API.spectable and are worth
  keeping: `path` takes segments rather than a joined string (the Page/Parameter
  split), and `status` is a separate step from `match response` (status and body
  come from different places).

  Two features worth considering for SpecTable:

  #### Explicit fuzzy matchers instead of bare words in a cell.
  Karate writes '#string', '#number', '#notnull', '#uuid', '#regex(...)'. The
  generated API.spectable used bare "string" and "number" for the same purpose,
  which is indistinguishable from expecting the literal word "string" -- and that
  ambiguity is exactly what let unverified expectations sit there looking
  checked. A marked syntax would let the generator emit a type assertion
  deliberately rather than the glue guessing from the text. See the placeholder
  section in SpecStudioVariousTests's Remaining Work.txt.

  #### An "each" form for arrays, and a way to address one element.
  This is really two features, and the second is the one SpecTable cannot express
  at all. Verified against Karate's own reference rather than from memory:

      # every element, one shape -- covers all 100 posts in one line
      * match each response == { userId: '#number', id: '#number', title: '#string' }

      # the shape can be named first, which reads like an Attributes block
      * def Post = { userId: '#number', id: '#number', title: '#string' }
      * match each response == Post

      # partial: each element has at least these, others allowed
      * match each response contains { userId: '#number' }

      # exactly 100 elements ('#[]' alone only asserts "is an array")
      * match response == '#[100]'

      # and one specific element, by index
      * match response[0] == { userId: 1, id: 1, title: 'sunt aut...' }

  Karate also asserts an exact set, deep and order-sensitive, by listing it:

      * match response ==
        """
        [ { userId: 1, id: 1, title: 'sunt aut...' },
          { userId: 1, id: 2, title: 'qui est esse' } ]
        """
      * match response == read('user-1-posts.json')   # or from a file

  **Most of this needs no language change -- it is a glue convention.** A
  multi-row table already produces a List of *String objects, so "these are
  exactly the elements" is a comparison the glue can make today: match the
  expected rows against the actual array as a set, failing on a missing row, an
  extra element, or a duplicate. Order-independence is then a property of the
  helper rather than of the notation, and is usually what is wanted from a
  filtered query. Addressing one element is the same story -- an index column,
  or a step whose glue takes the first row.

  What distinguishes the cases is the step wording, not the table:

      Then response array items match : Post     -- one shape, every element
      Then response posts are        : Post      -- exactly these rows
      Then first response post is    : Post      -- one element

  Each is a different glue method over the same generated type. Only the first
  exists today, which is why API.spectable's array scenario loops 100 items by
  hand and can state types but not values.

  For an exact set the table is the better notation -- an array of objects *is*
  a table, it diffs line by line, and a missing or extra row shows up plainly,
  where Karate's version is JSON pasted into a feature file.

  #### CompareOnly already covers "check only these columns".
  It is not a gap -- `: Post CompareOnly` fills every column the table does not
  show with ?DNC? instead of the field default, and the generated *String.equals
  and the hand-written glue both skip ?DNC?. So an exact-set table listing only
  id and title checks exactly those two and ignores userId and body. That is the
  answer to "the body is multi-line" for most cases: leave the column out.

  One restriction to know: the step regex is
  `:\s*(\w+)(?:\s+(Vertical|CompareOnly))?`, so a step takes *one* modifier.
  Vertical and CompareOnly cannot be combined. An exact-set table is horizontal
  anyway, so this bites only a single-object check that wants both.

  #### Multi-line values in a cell: the mechanism exists but is not connected.
  A Define can hold a docstring (`Define X =` followed by """ ... """), and a
  table cell can reference a Define with `=X`. Putting those together is the
  natural way to compare a multi-line value, and it does not work today.

  resolveValue in JavaGenerator.cpp (and identically in the Cpp and CSharp
  generators, so presumably all nine) resolves an `=` reference only for a
  *scalar* Define:

      if (d.name.compare(name, ...) == 0 && !d.isTable && !d.hasDocString)

  The `!d.hasDocString` guard excludes exactly the case wanted. A docstring
  Define referenced from a cell falls through to resolveCell and the cell keeps
  the literal text "=X", which then fails the comparison against real data.
  Docstring Defines are reachable from a bare step but not from a table.

  Relaxing that guard -- and emitting the multi-line text the way a step
  docstring already is (a Java text block, an escaped literal elsewhere) -- would
  make exact-set assertions work for values like jsonplaceholder's four-line
  bodies. Check all nine generators; the guard was written the same way in each
  one seen so far.

  Where each tool wins is clean, and worth being honest about. Karate is far less
  work for API testing. SpecTable is doing a different job: not API-specific,
  one specification into nine languages, and declared types so a Post is checked
  structurally rather than as loose JSON -- which is why bowling.spectable works
  in the same tool. If API.spectable were the whole job, Karate would be the
  better choice; its value here is showing that SpecTable can reach a live
  service, which is worth saying plainly rather than claiming parity.

### Sequence keyword: shows a sequence of operations where each step's Given is
  the previous step's output.

### State table: State/Event grid (states down the side, events across the
  top) filled in with transitions; generates glue code for every
  transition. Shorthand: "Given this state / When this event / Then this
  state." A state's target could reference a Define containing an if-clause
  for more complex transition logic.

### Karnaugh map style DataType/table with don't-cares ("DNC"), checked for
  completeness.

### Business Rule table with complex per-field conditions (e.g. ">10, >-10,
  >10 & <12, =10 | =12" — and/or/not plus comparison operators) instead of
  plain examples; if the rule fields are typed, auto-generate the Examples
  rows from the condition table.

[x] Analyze is off regular expressions. The last ten checks that reopened the
    file and matched line patterns are gone; every check about one file's
    contents reads the converter's parse tree (SpecTableModelChecks.cpp), and
    the four that remain in SpecTableAnalyzer.cpp are about names across files
    and read the index. Two things made it possible. The index now keeps each
    file parsed and hands Analyze the file with every sibling merged in and
    resolved -- the converter's own view before it generates -- so a set
    declared elsewhere is visible to a model check as it is to a generator.
    And the table checks became shared validators: validateStepTables now
    checks cell values too, and validateExamplesTables and
    validateAttributeDefaults are new, so the build warns about a bad value
    the way the editor does. Three rules moved into the parser outright, since
    they are rules of the language: a missing Import or Insert, and a ragged
    table row. Corpora: ErrorTests 46 -> 45 (one duplicate finding about the
    same column folded into the shared one), VariousTests 6 -> 8 (two values
    in Data Definition Error that the regex had missed because the set is
    declared twice), ExampleTests 0.

[x] An unresolvable field type is an error, and a DomainTerm resolves to what
    it stands for (b95a6e8). "DomainTerm Roll : Pins" already said a Roll is a
    Pins, so a field of type Roll is emitted as a Pins in all nine languages
    rather than refused; a type that resolves to nothing stops generation
    instead of producing a class that names it. Both live in the parser
    (resolveDomainTermTypes, validateFieldTypes) so Analyze and the converter
    say the same thing.

[x] A name declared as two kinds is an error at each declaration
    (checkNameDeclaredAsTwoKinds). "DataType Score" beside "| Score | Score |"
    is fine -- an attribute may share a type's name -- but an Entity and a
    DataType both called Score generate two classes of one name.

[x] =Name resolves in an Examples cell and in a Default column
    (resolveDefineReferences), where before only a step-table cell expanded
    it. Bowling's sentinels are now "Define TBR = -1" used as "=TBR" in the
    attribute defaults and "=TBS" in Score's ValidValues, so the DataTypes are
    integers with one reserved value rather than a number-or-word. The parser
    also stops a one-line Define's value at a trailing "#" comment, which the
    old text sentinels had hidden. Production Pins and Score in all nine
    languages treat -1 as the sentinel; 73/73 everywhere.

[x] Open a solution, or a file and the solution that owns it, from the command
    line (d72589d). main.cpp ignored argv entirely, so AlignThree always opened
    empty. Now `AlignThree Work.sspec`, `AlignThree Work.sspec Orders.spectable`,
    and `AlignThree Orders.spectable` -- the last walks up for the .sspec that
    owns the file, because a .spectable alone has no index, no configuration and
    no Analyze behind it. A file in no solution is refused with a message rather
    than opened bare. Registering the file association in the installer is still
    to do; scripts/alignthree.iss has no [Registry] section.

[x] A step may carry more than one modifier, in any order (2be7e7b). Vertical
    and CompareOnly answer different questions -- how the table is laid out, and
    which of its columns are compared -- and the restriction lived entirely in a
    regular expression that allowed one word after the type. Nothing downstream
    needed touching: the two flags were already orthogonal in every generator
    and in validateStepTables.

[x] EveryCell (6b2c700). A table naming an Entity had one reading, one row per
    instance with a column per attribute. EveryCell says the other: the table is
    a grid and each cell holds the text form of the named type. A DataType could
    already be read that way implicitly; this states it and extends it to
    Entities and Attributes blocks. The conversion reuses the text form that
    already existed -- fromText round-trips with toString -- written in each
    language's own idiom. A scalar or docstring Define may fill a cell, because
    =Name expands before the cell is converted. A table-form Define is refused
    with an error, in validateStepTables so that all nine languages and Analyze
    say the same thing.

[x] Uses is read by the parser and kept with the element it documents (08c3549).
    It was in the skip list and thrown away. Fixing that exposed an older bug: a
    named comment between a step and its table ended the table, which is exactly
    where the syntax document puts Uses, so the documented form had never
    worked.

[x] A table with no attribute set is an error, said once at the step (5c026b8),
    rather than two "unexpected table row" warnings that named no cause.

[x] A DomainTerm is refused as a field type (13e7623). Analyze called it legal
    while every generator emitted a class declaring a field of a type nothing
    writes. The message names the fix from the term's own declaration.

[x] Seven Analyze checks now read the parse tree instead of the file
    (13e7623, e66011c). checkAttributeFieldTypes, checkDomainTermColumnTypes and
    checkCleanup were the last three moved; checkCleanup turned out not to be an
    Analyze check at all -- "Cleanup may only contain Then and And" is a rule of
    the language, so it went to the parser.

[x] A shared file in common/ is merged, not replaced. Two of them were
    rewritten by each specification in turn, and each specification writes into
    the same folder, so only one specification's contribution survived.

    TableHelper.java held the toListListXxx grid converters. It was replaced on
    every write, so the last specification generated that had any grid step won
    and every earlier one lost its converters -- a converter would appear, then
    silently vanish when a sibling was generated afterwards. The union
    SpecStudioVariousTests needs is String, Integer, Boolean, Pins and
    FormattedDollar, which no single build could produce.

    ProductionHelper.java held the Entity-to-production conversions, and had the
    same hole in a quieter form: it was created only if absent, so whichever
    specification went first wrote it and it was never updated again. Every
    Entity declared in any other specification had no converters at all -- the
    committed file in SpecStudioVariousTests held Account and nothing else,
    while Address, ExchangeRates, Holding, Money and TwoAddresses were missing.
    Nothing failed, because the hand-written glue converts for itself; the file
    was simply four-fifths absent.

    Both now go through JavaGenerator::mergeHelperClass: read what is on disk,
    let this specification's methods win over their namesakes, keep everything
    else verbatim, write it back under a QLockFile -- the lock because
    Build > Project spawns every conversion at once and they all reach these two
    files, and an unguarded read-modify-write would lose a method exactly as
    replacing the file used to.

    The other eight generators do not have the same hole. That was tested rather
    than read: generate every specification into one folder in alphabetical
    order, generate them again in reverse into another, and compare the trees. A
    file that is merged comes out the same both ways; a file that is replaced
    holds whichever specification went last, so the trees differ and name it.
    All nine are stable under that test. Only Java generates these accumulating
    helpers at all -- the others convert in the glue, so they have no shared file
    to lose.

    The same probe found one more, in the production import added the day
    before: it asked whether the production folder had anything in it *on disk*,
    which depends on how many siblings had already been converted in this run.
    Generating a project into an empty folder therefore gave different files than
    regenerating it in place. It now asks the declarations, which every
    specification in a run sees identically through --context.

Share Changes (Commit + Push) / Get Others' Changes (Fetch)

Purpose: help the user review what changed, add a short description, confirm
sharing, and perform Commit + Push in one step — without exposing git jargon
to non-programmers, while still giving programmers what they expect.

Share Changes dialog layout:

1. Summary section (top)
   "You have changes ready to share. Review the updates below, then click
   Share." Shows count of changed items, optional "Last shared on..."
   timestamp, optional "up to date with others' changes" indicator.

2. Change list (center)
   Collapsible list of changed files (e.g. Customer.spec, Order.spec,
   Address.spec). Each expands to a friendly before/after diff view — no
   hunks, no patch syntax. Labels: Added (green), Removed (red), Updated
   (blue). Example:
     Customer.spec
       Name: Ken -> Kenneth
       Age: 42 -> 43

3. Description box (required)
   Label "Describe your changes" / subtitle "This helps others understand
   what you shared." This is the commit message, without calling it that.

4. Advanced options (collapsed, for programmers)
   Show actual git commit message; show commit hash preview; show branch
   name; checkbox "Push immediately after sharing" (checked by default);
   checkbox "Allow empty description".

5. Action buttons
   Primary: "Share Changes". Secondary: "Cancel", "Preview Details"
   (optional). Tooltip: "Saves your changes and makes them available to
   others. (Commit + Push)".

Behavior on Share Changes:
   Validate description -> Commit -> Push -> success toast "Your changes
   have been shared." If push fails: "Your changes were saved, but could
   not be shared. Try 'Get Others' Changes' first, then share again."
   (Programmers will recognize this as commit-succeeded/push-failed.)

Error Recovery dialog ("There Was a Problem Sharing Changes" / "...Getting
Others' Changes"):

1. Friendly summary: "Something went wrong while updating your project. You
   can try again, or ask a developer for help."

2. Simple explanation, one of:
   - Commit failed: "Your changes could not be saved safely."
   - Push failed: "Your changes were saved, but could not be shared with
     others."
   - Fetch failed: "The latest updates could not be downloaded."
   - Merge conflict: "Your changes conflict with updates from others."

3. "Details for Developers" (collapsed by default): real git error text
   (e.g. "Error: non-fast-forward update"), plain-language explanation,
   suggested fix (e.g. "Run: git fetch, then merge or rebase"), buttons
   View Diff / Open Merge Tool / Retry Push / Retry Fetch / Open Terminal,
   and metadata: current branch, remote branch, commit hash, upstream
   status, staged/unstaged changes, conflicting file list.

4. Conflict resolution section (if applicable): friendly message "Some of
   your changes conflict with updates from others. A developer can help
   resolve this." plus developer tools: Open Merge Tool, Show Conflicting
   Files, View Side-by-Side Diff, Abort Merge / Reset (developer only).

5. Action buttons: primary "Try Again", secondary "Cancel"; developer-only
   buttons Retry Commit / Retry Push / Retry Fetch / Open Merge Tool /
   Open Terminal / View Diff.

Related, not yet designed: Conflict resolution dialog, History/timeline
viewer, Branch creation dialog, Status panel, Git onboarding flow for
non-programmers.
